# ADR 0004: Ids, money and time rules for the port

- Status: **Proposed** (ids need owner confirmation, Q2)
- Date: 2026-11-02
- Deciders: repository owner

## Context

The current system uses integer autoincrement ids, integer "points" for money (2-decimal minor units), and Python's `zoneinfo` for the owner's timezone. A TypeScript port must define equivalents that behave the same on Node, WebViews and Safari, and that keep import/export and future sync possible.

## Decision

1. **Ids**: opaque string **UUIDv7** (lowercase canonical text), generated by the client or the server through an injected `IdGenerator`. Existing numeric ids are not preserved (pre-release; no production data). The API accepts an optional client-supplied id on create (idempotent).
   Lists are ordered by `(entry_date, created_at, id)` so ordering never depends on id magnitude.
2. **Money**: integer points in JavaScript `number`, guarded by `Number.isSafeInteger`; reject larger values with `MoneyError`. Amounts in requests are decimal strings; no floats ever represent stored money. Currency stays a field on money and accounts; no exchange logic in v1. The 2-decimal assumption is kept for parity (currencies with other exponents are a later feature).
3. **Time**: stored as UTC ISO-8601 instants; entry dates are the owner's local calendar dates. All zone math goes through one module built on `Intl.DateTimeFormat` with an IANA zone, with an injected `Clock`. Host timezone must never influence results (tested under several `TZ` values). If the spike shows `Intl` is inadequate on a target runtime, use a small FOSS timezone library instead (S5).
4. **Report floats** (percentiles, standard deviation, forecasts) are ported formula-for-formula and compared with documented tolerances; they are never stored.

## Consequences

- (+) Offline creation, safe import/merge, and sync-readiness; no collisions between devices.
- (+) Money math is exact; no BigInt overhead in hot paths.
- (-) The id type change touches the whole web app (`number` -> `string`); done once with the API v1 switch (MP-15).
- (-) Text ids make indexes larger than integers; acceptable at personal-ledger scale (benchmarked in the spike).
- (-) Safe-integer ceiling (~9e15 points); practically unreachable, but enforced.
- (-) `Intl` differences between engines can cause DST-edge discrepancies; mitigated by tests across Node, Chromium, WebView and Safari.

## Alternatives considered

- **Keep integer ids** (smaller change, but breaks offline creation, merging and sync-readiness; would need a second breaking change later).
- **UUIDv4**: no time ordering, worse index locality.
- **BigInt money**: unnecessary complexity and slower; rejected.
- **Decimal library** for money: not needed with integer points.
- **Temporal API** everywhere: not reliably available across targets yet **(verify)**; reconsider later.

## Verification / revisit when

Spike S4, S5 and the benchmark at 50k entries. Revisit if text-id indexes miss performance budgets.
